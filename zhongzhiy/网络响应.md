## 一、 HTTP 响应的解剖学基础

当浏览器或前端 App 向我们的 Axum 服务器发起一个网络请求后，服务器必须回传一个标准的 **HTTP 响应报文**。这个报文在网线（TCP 管道）里流动时，结构分为三个干净利落的部分：

1. **状态行（Status Line）**：紧跟在协议版本后面，由一个 **3 位数字的状态码** 和一个短小的文本描述组成。例如：`HTTP/1.1 200 OK` 或 `HTTP/1.1 409 Conflict`。**它是网络设备和前端最先读取的“红绿灯”。**
    
2. **响应头（Headers）**：一堆键值对，用来传递元数据。比如 `Content-Type: application/json`，告诉前端“我后面拉出来的货是 JSON 格式的，请用 JSON 解析器去解它”。
    
3. **响应体（Body）**：真正的业务核心数据，也就是我们在 Rust 里用 `json!({ ... })` 拼出来的货。
    

## 二、 状态码的“五大王国”

HTTP 状态码的第一位数字定义了响应的**核心大分类**：

- **`1xx`（信息性状态码）**：接收到请求，正在处理（在 Web 业务开发中极少直接接触）。
    
- **`2xx`（成功状态码）**：请求已被成功接收、理解并接受。例如 `200 OK`，`201 Created`（成功创建了资源）。
    
- **`3xx`（重定向状态码）**：资源搬家了，你去别的地方找。
    
- **`4xx`（客户端错误状态码）**：**划重点！代表“前端或者用户传过来的数据/行为有错”，服务器拒绝服务。**
    
- **`5xx`（服务器错误状态码）**：**划重点！代表“前端没做错，服务器后台自己拉胯了”（比如数据库断网、内存爆了、代码 Panic）。**
    

## 三、 为什么我们的业务错误要对应这些特定的网络状态码？（核心深度剖析）

在现代 RESTful API 设计哲学中，有一个极其核心的词叫做 **“语义化（Semantic）”**。网络上的各种中间件（比如 Nginx 网关、CDN 加速服务器、浏览器的缓存引擎）都是通过状态码来决定如何对待这个请求的。

我们来看看我们在 `SystemError` 里定义的那些错误，在 HTTP 的世界里分别对应着什么具体的网路语义：

### 1. `InvalidPrice` 与 `InvalidRoute` $\rightarrow$ `400 Bad Request`（坏的请求）

- **网络语义**：标准定义是“由于明显的客户端错误（例如，请求语法错误、格式无效、非法的参数数据），服务器无法或不会处理该请求”。
    
- **为什么对应**：用户传过来的票价是 `-50` 块钱，或者配置的终点站序号居然小于起点站序号。这种逻辑上的荒谬，属于**典型的客户端输入参数校验失败**。前端不应该允许用户输入这种数据，既然传过来了，后端就用 `400 Bad Request` 严肃拒绝，意思是：**“你的请求参数不合法，回去检查好了重新发！”**
    

### 2. `DuplicateTrain` 与 `DuplicateClerk` $\rightarrow$ `409 Conflict`（资源状态冲突）

- **网络语义**：标准定义是“由于请求与目标资源的**当前状态冲突**，导致请求无法完成。此代码仅在预期用户能够解决冲突并重新提交请求的情况下才是合法的”。
    
- **为什么对应**：前端发来的请求本身是完全合法的（ID是数字，名字是字符串，格式挑不出任何毛病），但是**因为此时数据库里已经躺着一个相同 ID 的车次了**。这就触发了“请求意图”与“服务器系统当前状态”的**严重冲突**。返回 `409` 就是精确地告诉前端：“你提交的东西格式没问题，但是系统里已经有重名的了，请换个 ID 或者换个名字再来！”
    

### 3. `SeatConfig`（区间占座冲突）$\rightarrow$ `409 Conflict`

- **为什么这也是 409，而不是 400？**
    
    这是最彰显后端架构师功底的细节。
    
    - 如果座位号传了 `-1`，或者座位号超出了火车的总座位数，这是 `400 Bad Request`（参数本身非法）。
        
    - 但现在座位号是 `7`（完全合法），区间是 `1站到2站`（完全合法）。当你点下买票时，票偏偏被抢先一步的小人买走了。这叫**并发状态竞争冲突**。
        
    - 使用 `409 Conflict` 是在以标准的网络协议语言告诉前端：**“你由于网络竞态条件慢了一步，座位刚刚被别人占了（状态冲突），请重新选座刷新再来。”**
        

### 4. `DatabaseError` $\rightarrow$ `500 Internal Server Error`（服务器内部错误）

- **网络语义**：标准定义是“服务器遇到了不知道如何处理的突发情况，导致它无法完成对请求的处理”。
    
- **为什么对应与安全防御**：当遇到数据库断网、表结构损毁、或者 SQLx 连接池爆满时，前端乘客是没有任何过错的，参数也完全合法。这是我们服务器自身的灾难。
    
- **🚨 工业级至关重要的安全规范（防拖库漏洞）**：底层的 SQL 报错（比如：`Connection reset by peer` 或 `Table railway_db.tickets does not exist`）**绝对、绝对不能**直接随着网络原封不动地发回给浏览器！
    
    - 如果你把这些详细的数据库内脏错误吐给前端，黑客就可以通过故意制造错误，来精确刺探你的数据库表结构、字段名、中间件版本，进而实施精准的 SQL 注入或权限绕过。
        
    - 正确的做法是（就像我们在代码里写的一样）：利用 `eprintln!` 把血淋淋的底层真实错误**死死扣留在服务器的后台日志里**，转过身来，戴上一副客气的面具，给前端返回一个模糊的 `500` 状态码和一句统一的敷衍：`"数据库繁忙，请稍后再试"`。既保护了隐私，又满足了语义。
        

## 四、 为什么不图省事，全部返回 `200 OK`？

很多初学者喜欢搞一种骚操作：不管后台发生什么惊天大爆炸，HTTP 状态码一律返回 `200 OK`，然后在返回的 JSON 里塞一个自定义的 code：

JSON

```
// ❌ 工业界极度唾弃的反模式（业务与协议严重割裂）
HTTP/1.1 200 OK
{
    "code": 500,
    "msg": "数据库炸了"
}
```

这种做法在工业级的大型分布式架构中会引发严重的灾难：

1. **API 网关监控失效**：像 Nginx、Kong、阿里云 SLB 这样的专业网关，是通过监控网络流中的 **HTTP 状态码 4xx/5xx 的异常比例** 来自动触发短信报警或自动熔断隔离的。如果你全回 200，网关会认为你的系统健康度是 100%，哪怕你的数据库已经炸了三天三夜，报警系统也一片死寂。
    
2. **CDN 缓存灾难**：很多网络加速节点（CDN）看到 `200 OK`，就会自动把这个响应缓存起来。如果某个乘客因为选座冲突收到了一个假装是 200 的“座位已被锁”报错，CDN 可能会把这个报错页面缓存 10 分钟。接下来，全世界所有路过这个节点的正常乘客，都会莫名其妙地看到这个报错缓存，系统直接崩溃。
