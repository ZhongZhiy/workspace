## 现代系统常用的64位虚拟地址有多少空间?
$ 2^{64}$
实际上只使用低48位或57位

## DRAM缓存是**全相联**的, 所以它的物理页替换策略是?
任意物理页都可以包含任意虚拟页

## **按需页面调度** 和 **独立的虚拟地址空间** 的结合, 对系统中内存的使用和管理造成了深远的影响, 特别地, VM简化了==链接和加载==, ==代码和数据的共享==, 以及应用程序的==内存分配==
- 简化链接: 独立的地址空间可以让每个程序都使用系统的基本格式, 例如代码段总是从0x400000开始, 栈总是用户地址空间的最高部分向下生长... 这样的一致性简化了链接器的设计
- 简化加载: 操作系统给这个程序创建一个页表, 并且全部标记为*未缓存*, 直到需要的时候才加载对应的页面,
- 简化内存分配: 在虚拟内存中分配一块空间可以映射到任意的不连续的物理地址上, 不必要分配连续的物理内存页面

## 虚拟内存会映射到离散的物理内存中反而不会破坏局部性?
1. 在程序运行的时候, CPU和Cache看到的是**虚拟地址**, 当CPU访问虚拟地址A的时候, Cache会把它周围地址一起加载到高速缓存中, 地址翻译(VA->PP)发生在MMU中, 对于CPU和Cache来说, 只要在**虚拟地址空间**中是连续的, 那么它们处理的就是连续的字节流
2. 物理地址虽然是离散分配的, 但是它是以**页(Page, 通常为4K)**为单位, 对于一个页来说, 物理地址一定是连续的， 而且程序局部性一般也不会超过4K
3. TLB(转址旁路缓存)可能被破坏, 如果地址十分分散, 那么MMU就必须频繁更换页表项, TLB缓存不够, CPU就会去内存查询多级页表导致性能下降

# 数据库

## [mysql]
在建立表的过程中制定索引的语法
---
```sql
CREATE TABLE items (
    id INT AUTO_INCREMENT,
    item_code VARCHAR(20) NOT NULL,
    item_name VARCHAR(100),
    description TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    -- 1. 主键索引 (Primary Key)
    PRIMARY KEY (id),
    
    -- 2. 唯一索引 (Unique Index)
    UNIQUE INDEX uk_item_code (item_code),
    
    -- 3. 普通索引 (Index/Key)
    INDEX idx_name (item_name),
    
    -- 4. 复合索引 (Multiple Columns)
    INDEX idx_name_time (item_name, created_at),
    
    -- 5. 全文索引 (Fulltext)
    FULLTEXT INDEX ft_desc (description)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## [mysql]
使用`alter table`语法添加索引
---
添加普通索引:
```sql
ALTER TABLE items ADD INDEX idx_item_name (item_name);
```
添加唯一索引
```sql
ALTER TABLE items ADD UNIQUE INDEX uk_item_code (item_code);
```
添加主键索引
```sql
ALTER TABLE items ADD PRIMARY KEY (id);
```
添加前缀索引
```sql
ALTER TABLE items ADD INDEX idx_short_name (item_name(10));
```
